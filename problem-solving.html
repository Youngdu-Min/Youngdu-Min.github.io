1.콘텐츠 75% 이상을 하나의 코어 위로: 교육 콘텐츠 코어·베이스 스크립트 설계Putting 75%+ of the content on one core: designing the core/base scripts for educational content

문제

  • 2023·2024 대형 업데이트에서 개발자 8명이 동시에 새 콘텐츠를 만들어야 했다.
  • 교육 콘텐츠는 대부분 "문제 출제 → 문제별 상호작용 → 채점 → 결과 저장"이라는 같은 흐름을 갖는데, 기존 콘텐츠는 이 흐름을 콘텐츠마다 따로 들고 있었다.
  • 새 구조를 만들더라도 이미 서비스 중인 레거시 콘텐츠를 버릴 수는 없었다.

해결

  • 추상 클래스에는 확정적으로 겹치는 흐름만 넣었다. 출제·채점·저장처럼 모든 콘텐츠가 똑같이 거치는 단계만 베이스가 맡고, 콘텐츠마다 다른 "문제별 상호작용"은 파생 클래스가 구현한다.
  • 선택 기능은 인터페이스로 붙이게 했다. 드래그 앤 드롭, 그래프처럼 일부 콘텐츠만 쓰는 기능은 파생 클래스에 인터페이스를 추가하는 방식으로 조합한다. 인터페이스와 코어 사이의 통신 부분은 미리 구현해 두어서, 콘텐츠 개발자는 원하는 인터페이스를 붙이기만 하면 동작한다.
  • 설정값은 ScriptableObject로 분리했다. 코드를 고치지 않고 콘텐츠를 조정할 수 있다.
  • 레거시 호환을 설계 조건으로 두었다. 기존 콘텐츠는 베이스를 상속받고, 베이스와 겹치는 코드를 지우는 것만으로 새 구조로 옮겨진다.
  • 사용법은 Slack 고정 공지로, 복잡한 내용은 Notion 문서로 공유했다. 내 파트를 만들면서 코어에 필요한 개선점을 찾으면 코어에 반영해 유지보수했고, 여러 콘텐츠에서 쓰이는 교육 실습 상호작용(드래그 앤 드롭, 그래프 등)은 공용 모듈로 분리했다.

왜 추상 클래스와 인터페이스를 나눴나

  • 베이스에 "아마 공통일 것 같은" 기능까지 넣으면, 그 기능이 필요 없는 콘텐츠도 베이스를 따라야 하고 예외 처리가 베이스에 쌓인다.
  • 그래서 베이스에는 바뀌지 않을 흐름만 두고, 바뀌거나 선택적인 기능은 인터페이스로 빼서 콘텐츠가 필요한 것만 고르게 했다.

결과

  • 독립적으로 구현된 콘텐츠를 제외한 약 75% 이상의 콘텐츠가 이 코어 위로 옮겨지거나 새로 개발됐다.
  • 팀원들이 베이스를 파생해 각자 콘텐츠를 개발했고, 공통 상호작용은 모듈을 가져다 쓰는 방식으로 정리됐다.

Problem

  • In the 2023 and 2024 major updates, eight developers had to build new content at the same time.
  • Most educational content follows the same flow (question → per-question interaction → grading → saving results), but each existing piece carried its own copy of that flow.
  • Even with a new structure, we couldn't throw away the legacy content that was already live.

Solution

  • The abstract class holds only the flow that is certain to be shared. The base handles the steps every piece goes through the same way, such as question, grading and saving, while each derived class implements its own per-question interaction.
  • Optional features attach through interfaces. Features only some content needs, like drag-and-drop or graphs, are composed by adding an interface to the derived class. The wiring between those interfaces and the core was already in place, so a content developer just adds the interface they need and it works.
  • Settings live in ScriptableObjects. Content can be tuned without touching code.
  • Legacy compatibility was a design requirement. Existing content moves to the new structure just by inheriting the base and deleting the code that overlaps with it.
  • Usage went into a pinned Slack post, and the details into Notion. While building my own part, I fed improvements the core needed back into it, and split educational interactions used across many pieces (drag-and-drop, graphs, etc.) into shared modules.

Why split abstract classes and interfaces

  • If the base also takes on features that are "probably shared," content that doesn't need them still has to follow the base, and exception handling piles up inside it.
  • So the base keeps only the flow that won't change, and anything that changes or is optional moves into an interface, letting each piece pick only what it needs.

Result

  • About 75%+ of the content, excluding independently built pieces, was migrated onto this core or newly built on it.
  • Teammates built their content by deriving from the base, and shared interactions were handled by pulling in modules.

2.나 없이도 빌드가 되게: 빌드·배포 절차 문서화와 자동화Builds that don't depend on me: documenting and automating the build and release process

문제

  • iOS·Android·WebGL 세 플랫폼의 빌드·심사·배포 절차가 단순 txt 파일로만 남아 있었다.
  • 절차를 아는 사람이 없으면 빌드가 막히는 구조였다.

해결

  • 빌드 절차를 Notion 문서로 다시 정리했다. 단계마다 체크박스를 두고, 세부 내용은 접었다 펼칠 수 있게 만들었다.
  • 자동화할 수 있는 단계는 bat 스크립트로 만들었다.
  • 빌드 전에 확인해야 하는 파일을 한곳에 모아 볼 수 있는 Unity 에디터 툴을 만들었다.

결과

  • 다른 팀원들도 내 도움 없이 문서를 따라 빌드·배포를 진행할 수 있게 됐다.

Problem

  • The build, review and release steps for iOS, Android and WebGL existed only as a plain text file.
  • If the person who knew the steps wasn't around, builds stalled.

Solution

  • Rewrote the build procedure as a Notion document, with a checkbox for each step and collapsible details.
  • Turned the steps that could be automated into batch scripts.
  • Built a Unity editor tool that gathers the files to check before a build in one place.

Result

  • Other teammates could build and release on their own by following the document.

3.빌드 용량 약 70% 절감 (1GB 이상 → 350MB 이하)Cutting build size by about 70% (1 GB+ → under 350 MB)

문제

  • 이미지 리소스가 많아 앱 용량이 1GB를 넘었다.
  • 압축 포맷을 적용하려면 이미지마다 크기를 4의 배수로 맞추는 반복 작업이 필요했다.

해결

  • 먼저 범용 슬라이싱 UI 이미지로 대체할 수 있는 에셋을 교체하고, 사용하지 않는 에셋을 정리해 리소스 수 자체를 줄였다.
  • 이미지 크기를 4의 배수로 맞추는 에디터 툴을 만들어 텍스처 압축을 일괄 적용했다.
  • 대부분 슬라이싱 스프라이트라 크기 조정에 따른 품질 문제가 거의 없었다.

결과

  • 전 플랫폼 빌드 용량 1GB 이상 → 350MB 이하 (약 70% 절감)

Problem

  • With so many image resources, the app was over 1 GB.
  • Applying compressed formats meant resizing every image to multiples of 4, a repetitive manual job.

Solution

  • First replaced assets that a generic sliced UI image could cover and removed unused ones, cutting the number of resources itself.
  • Built an editor tool that resizes images to multiples of 4, then applied texture compression in bulk.
  • Since most of them were sliced sprites, resizing caused almost no quality issues.

Result

  • Build size across all platforms: over 1 GB → under 350 MB (about 70% smaller)

4.학교 크롬북에서 멈추던 WebGL: 탭당 2GB 가까운 메모리 최적화WebGL that froze school Chromebooks: optimizing memory that neared 2 GB per tab

문제

  • WebGL 탭 하나가 메모리를 2GB 가까이 사용했다.
  • 학교에서 주로 쓰는 저사양 크롬북·웨일북에서 탭을 여러 개 열면 브라우저가 멈췄다.

해결

  • Addressables 등으로 필요한 리소스만 불러오고 해제하도록 메모리를 최적화했다.
  • 운영 측면에서는 서비스를 여러 탭으로 열지 않도록 공지했다.

결과

  • 이후 메모리 초과 문제가 개발팀에 다시 보고되지 않았다.

Problem

  • A single WebGL tab used close to 2 GB of memory.
  • On the low-end Chromebooks and Whalebooks common in schools, opening several tabs froze the browser.

Solution

  • Optimized memory so only the resources needed are loaded and then released, using Addressables among other things.
  • On the operations side, posted a notice asking users not to open the service in multiple tabs.

Result

  • No memory-overrun problems were reported to the development team after that.

5.그리기 기능의 메모리 누적으로 인한 모바일 크래시Mobile crashes from memory piling up in the drawing feature

문제

  • 그리기 기능이 획을 그릴 때마다 전체 화면을 스택에 새로 쌓았다.
  • 메모리가 계속 늘다가 앱이 종료됐고, 메모리가 적은 모바일 기기에서 주로 발생했다.

해결

  • 화면 데이터를 캐싱해 두고 갱신하는 방식으로 재설계했다.

결과

  • 메모리 누적과 크래시를 해결했다.

Problem

  • The drawing feature pushed a new full-screen copy onto a stack with every stroke.
  • Memory kept growing until the app quit, mostly on mobile devices with little memory.

Solution

  • Redesigned it to cache the screen data and update it in place.

Result

  • Fixed both the memory buildup and the crashes.

6.PC와 모바일이 지원하는 텍스처 압축 포맷이 다른 WebGL 교구 서비스A WebGL teaching-aid service where PC and mobile support different texture compression formats

교육 기업 납품 교구 WebGL 서비스 · 3인(선임 2명과 함께) · 2025.01 – 03 · 기존 커스텀 UI 환경으로 교구 10종 이상을 UI 이벤트·인터랙션으로 구현

WebGL teaching-aid service delivered to an education company · team of 3 (with 2 senior developers) · 2025.01 – 03 · Built 10+ teaching aids with UI events and interactions on an existing custom UI framework

문제

  • PC와 모바일 GPU가 지원하는 텍스처 압축 포맷이 다르다.
  • 한 포맷으로만 만들면, 그 포맷을 지원하지 않는 기기에서는 텍스처를 런타임에 풀어 올려야 해서 메모리와 로딩 부담이 커진다.

해결

  • 처음에는 Unity 공식 방식대로 압축 포맷별로 빌드를 나누고, index.html에서 JavaScript로 맞는 빌드를 고르게 구현했다.
  • 이후 선임 요청으로, JavaScript가 접속 기기를 판별하고 기기에 맞는 포맷의 AssetBundle을 불러오는 방식으로 바꿨다.
  • 플랫폼별 셰이더도 함께 대응했다.
  • WebGL은 실행 중 해상도가 바뀔 수 있어, 필요한 교구에는 해상도 변경 콜백을 연결했다.

결과

  • 하나의 WebGL 서비스로 PC와 모바일 웹 모두에서 쓰는 교구를 납품했다.

Problem

  • PC and mobile GPUs support different texture compression formats.
  • Shipping a single format means devices that don't support it have to decompress textures at runtime, which costs memory and loading time.

Solution

  • At first I followed Unity's official approach: separate builds per compression format, with JavaScript in index.html picking the right one.
  • Later, at a senior developer's request, I switched to having JavaScript detect the device and load AssetBundles in the matching format.
  • Also handled platform-specific shaders.
  • Because WebGL resolution can change at runtime, I hooked up a resolution-change callback for the teaching aids that needed it.

Result

  • Delivered teaching aids that run on both PC and mobile web from a single WebGL service.
